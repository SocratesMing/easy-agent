# 会话手动归档管理设计

日期：2026-10-30 · 状态：最终设计，待实现

## 1. 功能范围

归档用于整理日常会话列表。提供单条归档、归档管理、取消归档和删除；FastAPI 后端、Vue2 与 Vue3 两个前端同步实现。

- 归档后从日常列表移除，在归档管理中显示；取消归档后回到日常列表。
- 归档只改变归档标记，保留消息、文件、待办、用量、工作区、置顶状态及创建和最后活跃时间。
- 归档不冻结会话。通过已有入口访问时，读取和继续使用沿用原规则，不自动取消归档；归档也不停止生成或作废待审批操作。
- 删除复用现有会话删除流程，需二次确认，删除后无法在应用中恢复。

时间语义：归档和取消归档操作本身不修改 `created_at / updated_at`；归档期间若继续聊天或后台生成写入消息，仍按现有规则更新 `updated_at`。取消归档按当时实际的最后活跃时间排序，不回写归档前的时间，也不保证恢复到归档前的列表位置。

## 2. 数据与 API

### 数据

在 `sessions` 表增加 `archived INTEGER NOT NULL DEFAULT 0`，API 中使用 boolean。旧会话默认未归档，迁移支持 SQLite / MySQL，重复启动不改变已有数据，并按现有规范递增 `SCHEMA_VERSION`。

归档更新只写该字段，不调用会改写消息或最后活跃时间的通用保存逻辑；其他会话保存也不得覆盖该字段。重复设置同一状态直接成功。沿用现有仓储分层，不新增归档表或独立归档服务。

### 接口

| 接口 | 约定 |
| --- | --- |
| `PUT /agent/sessions/{session_id}/archive` | 请求 `{"archived": true}` 归档，`false` 取消归档；成功返回 `{"status":"updated","session_id":"…","archived":true}`。 |
| `GET /agent/sessions` | 增加 `archived`，默认 `false`；支持归档页使用的标题搜索 `q`，复用 `limit / offset` 分页；响应仍为会话数组。 |
| `GET /agent/sessions/count` | 增加 `archived / q`，返回相同筛选条件下的数量；不传 `archived` 时保留现有全部可见会话总数语义。 |
| 现有详情与历史接口 | 返回数据增加 `archived`，保留原有访问能力。 |
| `DELETE /agent/sessions/{session_id}` | 直接复用，不新增删除接口。 |

列表数据增加 `archived`。日常列表及其计数显式传 `archived=false`，归档管理传 `true`。两类列表继续排除现有内部定时任务会话。

日常列表保持置顶优先、最后活跃时间倒序；归档列表按最后活跃时间倒序，不受置顶影响，同时间以会话 ID 保持稳定顺序。标题搜索为去除首尾空白后的字面包含匹配，列表与计数使用相同条件，在数据库分页前筛选，不能从日常列表前 50 条中拼出归档结果。

所有接口使用 JWT 中的当前用户。归档写入同时限定会话 ID 和用户名，不存在与非本人会话统一返回 404；非法参数返回 422。沿用现有参数化查询、请求与错误处理方式。

## 3. 页面行为

### 手动归档

在会话行“更多”菜单增加“归档”，普通与置顶会话均可操作。

点击后确认：“将「{标题}」移至归档？消息和文件会保留，可在归档管理中取消归档。”确认后提交，期间禁用该会话的重复操作；成功刷新日常列表，提示“已归档”，失败保留原行并提示原因。

归档的目标正在主聊天或 AI 侧边栏显示时，仅让展示该会话的实例回到新建会话欢迎页，不创建数据库会话。复用已有切换逻辑中保存会话状态和重置展示的部分，不复用删除专属的缓存、流式标记及待审批标记清理。将对应视图的当前选择持久化为新建会话欢迎页，避免仅删除记录后触发默认选中其他会话；同时处理流式恢复路径，防止刷新后自动重新打开该目标。保留其他会话及其草稿。页面退出展示不应中断后台任务或清除服务端会话数据。

### 归档管理

底部用户菜单增加“归档管理”，点击打开弹层，复用现有弹层组件和键盘交互。弹层打开不切换背景会话。

弹层内容保持简单：

- 标题搜索框、会话数量。
- 扁平会话列表，每行显示标题、“取消归档”和“删除”。
- 服务端分页，每页 20 条；搜索变化回第一页。

点击标题或行背景不打开历史。列表固定按最后活跃时间倒序，不增加排序选择器或归档时间字段。

| 操作 | 行为 |
| --- | --- |
| 取消归档 | 无需确认；成功刷新归档列表和日常列表，提示“已取消归档”，弹层保持打开，不自动切换会话。恢复后保留原置顶状态，不修改当时的最后活跃时间，按该时间参与日常列表排序。 |
| 删除 | 确认“确定删除「{标题}」吗？该会话的消息和文件将被删除，删除后无法恢复。”确认后调用现有删除接口，成功刷新列表并沿用现有删除同步。 |

同一行操作期间禁用两个按钮，删除目标绑定确认时的会话 ID。操作后若当前页已空且不是第一页，回到有效页。

### 状态与反馈

日常列表与归档列表独立保存。参考项目已有请求取消或版本控制方式，为两类列表补齐过期响应保护，避免归档操作、搜索、关闭弹层及切换用户后的旧响应回填；同页主聊天与侧边栏通过现有事件机制同步，但归档事件不得沿用删除事件的清理语义。

区分加载、无归档、搜索无结果和读取失败，失败时允许重试。写入成功但刷新失败时提示刷新失败，不把已完成操作显示为失败。打开弹层时重新加载；登录失效沿用认证流程并清空相关数据。

按 ID 打开会话继续沿用已有入口，不能将“不在日常列表中”当作已删除。已归档会话即使被打开，也保持归档状态且不重新出现在日常列表。

## 4. 验收

重点验证以下场景，补充对应后端与前端测试，并在两个前端检查交互：

1. 旧库升级后原会话正常显示；普通和置顶会话可归档、恢复，重复操作安全，操作本身不改变消息、文件、置顶及时间；归档期间正常聊天产生的时间变化不应被回滚。
2. 日常列表与归档列表筛选正确；超过 50 条会话时搜索、分页和计数仍正确，取消归档后按保留的置顶状态及实际最后活跃时间排序；搜索含 `%`、`_`、转义字符时仍按字面匹配，SQLite / MySQL 分别验证。
3. 用户之间数据隔离，越权操作返回 404；归档状态不会被后续聊天保存覆盖。通过已有按 ID 入口打开归档会话并继续聊天后，仍不进入日常列表。
4. 归档当前会话后对应视图回到欢迎页；后台仍在生成时立即刷新，也不自动重开该会话。后台回复结束、标题更新及流式回放不得将归档会话重新插入日常列表，也不得向欢迎页或其他会话插入错误会话行；其他会话和草稿不受影响，后台生成及待审批数据保留。
5. 删除取消时无请求，确认后复用现有清理流程；请求失败、迟到响应及写成功后刷新失败均有正确反馈。覆盖归档前已发出的日常列表请求晚返回，以及退出登录或切换用户后旧响应返回的场景。

## 5. 基于当前项目的可行性核查与实施注意事项

核查日期：2026-10-30。结论：现有项目可以实现本设计，未发现必须重构整体架构的阻碍。以下为落实前述要求所需的代码适配，不增加功能范围。本次结论来自设计与源码静态核查，未执行迁移、运行测试或浏览器验证；不代表功能已经实现。

### 5.1 已具备的后端基础

- [schema.py](../../easy_agent/db/schema.py) 已有 SQLite / MySQL 幂等补列、迁移锁与结构版本检查。增加字段沿用 `_create_sessions_table / _ensure_column`，并递增 `SCHEMA_VERSION`；部署使用 `EASY_AUTO_MIGRATE=0` 时需通过现有迁移脚本先升级。
- [session_repository.py](../../easy_agent/db/session_repository.py) 与 [repositories/sessions.py](../../easy_agent/db/repositories/sessions.py) 已有会话仓储分层，列表和计数由数据库查询完成，可在原查询中增加归档筛选、搜索与排序。
- [api/sessions.py](../../easy_agent/api/sessions.py) 已有列表、计数、详情、历史和删除接口；[session_ownership.py](../../easy_agent/db/session_ownership.py) 已实现本人归属校验以及不存在、非本人统一 404。归档写入仍须在 SQL 中同时限定 ID 与用户名。
- 当前通用会话保存只显式更新标题、时间、用户名，消息写入也只更新消息数量和时间，并不会整行覆盖新增字段。增加 `archived` 时应保留这种显式更新方式；读取链路须同步补齐数据库模型、SQL 投影和 API 响应模型。

### 5.2 流式结束不能依据日常列表缺项直接补入会话

当前回复结束并带标题时，处理器发现会话不在 `sessions` 中就直接插入，未区分归档会话。已归档会话通过已有入口打开并继续聊天后，可能被重新加入日常列表；归档期间清空或切换当前视图，还可能因处理器使用 `currentSessionId` 而插入空 ID 或其他会话的错误行。

开发入口：Vue2 的 [App.vue](../../frontend-vue2/src/App.vue) 中 `createStreamChunkHandler`、[services/chunkHandler.js](../../frontend-vue2/src/features/chat/services/chunkHandler.js)；Vue3 的 [composables/useStreamChunks.js](../../frontend/src/features/chat/composables/useStreamChunks.js)、[services/chunkHandler.js](../../frontend/src/features/chat/services/chunkHandler.js)。这些路径均须按事件所属会话 ID 和归档状态处理列表更新，不能把“当前日常列表中没有”作为新会话的充分条件。

### 5.3 当前选择与流式恢复是两条独立路径

两个前端的 `App.vue` 都有 `tryAttachLiveStream`：从 `STREAM_STATE_KEY` 恢复活跃任务，并以 `switchTo: true, displayed: true` 自动展示最近的流式会话。因此，仅重置 `ACTIVE_SESSION_KEY` 仍不能满足“刷新不自动重开”。

开发时须同时检查当前选择恢复、流式恢复和侧边栏页面会话记录。归档退出展示后，任务仍可后台挂载，但不得仅因其还在生成而自动切回该会话；不能通过删除全部流式记录来规避，否则会影响后台状态恢复及其他会话。侧边栏相关入口为两个前端 `AiSidebar.vue` 的 `pageSessions / preferPageSession / rememberPageSession`。

### 5.4 可以复用事件机制，不能直接复用删除处理

两个前端的 `chatStore.js` 已有主页面与侧边栏共享状态及事件总线。当前 `session-removed` 表示删除：接收方会删除会话缓存，部分回退逻辑会打开列表第一条；删除操作还会移除流式及待审批标记。这些行为不能用于归档。

归档应沿用事件总线传递归档状态变化，由展示目标会话的实例保存必要状态并回到欢迎页，保留后台任务与审批数据；其他实例只同步相应列表和归档状态。真正删除时继续使用现有删除同步。

开发入口：两个前端 `features/chat/mixins/chatSession.js` 的 `onPeerSessionRemoved / handleDeleteSession / fallbackAfterSessionRemoved`、Vue2 `App.vue` 的删除处理，以及 Vue3 [useAiSidebarBridge.js](../../frontend/src/features/chat/composables/useAiSidebarBridge.js)。

### 5.5 按 ID 访问与响应转换需要同步适配

Vue2 `App.vue` 的 `restoreInitialSession` 对已有 `?session=<id>` 入口先检查目标是否在已加载的日常列表中。增加归档筛选后，该检查会把存在的归档会话排除；必须通过现有详情接口确认访问权限和是否存在，不能只看列表。两个前端对持久化当前会话的恢复也存在列表成员判断，需按前述当前选择与显式打开的语义分别处理。

两个前端 [api/chat.js（Vue2）](../../frontend-vue2/src/api/chat.js)、[api/chat.js（Vue3）](../../frontend/src/api/chat.js) 的 `getChatHistory` 实际调用详情接口，且重新组装返回对象。目前只保留消息、待办、用量与上下文长度，实施时须透传 `archived` 并维护会话状态，避免后端已返回字段而前端丢弃。

### 5.6 日常列表旧响应与字面搜索不能遗漏

当前两个前端主页面及会话 mixin 的 `loadSessions` 都会直接用响应覆盖共享列表，尚未具备本设计所需的归档操作与用户切换版本保护。保护范围须包含日常列表及其刷新调用，不能只处理归档弹层；归档成功后，较早发出的日常列表响应不得把目标重新放回列表。

标题搜索若使用 `LIKE`，参数化查询只能解决 SQL 参数安全，不能让 `%`、`_` 自动变成字面字符。列表与计数须采用一致的字面匹配和转义规则，并验证 SQLite / MySQL 的对应行为。
