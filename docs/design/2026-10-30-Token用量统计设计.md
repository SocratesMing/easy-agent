## 1. 功能与统计规则

在“设置 → Token 统计”增加四张统计卡和一张每日趋势图，Vue2、Vue3 同步实现。

| 功能 | 规则 |
| --- | --- |
| 今天 | 北京时间今天00:00至查询时刻 |
| 七天 | 含今天的最近7个自然日 |
| 一个月 | 含今天的最近30个自然日，副标题“近30日” |
| 总共 | 功能启用以来已记录的全部用量 |
| 每日趋势图 | 默认近7日，可切换近30日；每个模型一条线，缺失日期补0 |
| 用户范围 | 按JWT鉴权得到username，再查询用户记录取得真实user_id |
| 总Token | `input_tokens + output_tokens`，思考和缓存Token不额外相加 |

统一使用 `Asia/Shanghai`，按模型调用结束时间归日，查询区间为 `[起点, 查询时刻)`。例如北京时间2026-10-30中午查询，近7日是10月24日至30日，近30日是10月1日至30日，分别恰好7/30个点。

只统计应用取得的完整真实usage，不估算未上报用量，不回填上线前历史。删除或归档会话不删除统计记录，重启后累计保持。统计范围包含该用户触发的聊天、判定/预检、摘要、记忆、专家生成、知识问答、补全、提示词增强和定时任务；不是只计算最终回答的 Token，也不折算金额。
**数据链路：模型接口返回usage → 按调用记录到数据库 → SQL汇总 → 页面展示。**

## 2. 采集：每次模型调用结束记录一次

### 2.1 数据来源与采集方式

Token用量由模型供应商在API响应中返回。当前所有实际模型路径都是 OpenAI 兼容协议，因此统一校验原始 `prompt_tokens`、`completion_tokens`，映射为账本输入/输出字段。LangChain 的 `usage_metadata` 继续服务现有聊天展示，仅作核对，不作为缺失原始字段时的补值来源。例如一次LangChain响应携带：

```json
{
  "input_tokens": 1000,
  "output_tokens": 200,
  "total_tokens": 1200
}
```

应用将输入1000、输出200保存为一条调用记录，展示总量时计算得到1200。

**两条调用路径统一字段后写入同一张表，每次独立调用各存一行，查询时再汇总。** 字段映射如下：

| 调用路径 | 输入来源 | 输出来源 | 数据库目标字段 |
| --- | --- | --- | --- |
| LangChain（由 `ReasoningChatOpenAI` 提取原始完整 usage） | `usage.prompt_tokens` | `usage.completion_tokens` | `input_tokens`、`output_tokens` |
| OpenAI SDK直调 | `completion.usage.prompt_tokens` | `completion.usage.completion_tokens` | `input_tokens`、`output_tokens` |

例如同一用户先增强提示词，再发送聊天，产生两次独立模型调用：

| 调用 | event_id示例 | input_tokens | output_tokens |
| --- | --- | ---: | ---: |
| 提示词增强（SDK直调） | `sdk:xxx` | 100 | 50 |
| 聊天模型（LangChain） | `lc:yyy` | 1000 | 200 |

两次调用分别写入 `token_usage`。在同一用户、同一统计窗口内，SQL累加两行的输入和输出：`(100 + 50) + (1000 + 200) = 1350 Token`。不需要将两行合并或覆盖为一行。

**采集规则：一次真实模型调用，只记录一次完整用量。**

- **接入点**：在 `easy_agent/agent/model.py:create_model` 安装一次callback；SDK适配仅用于绕过LangChain的直调，不拦截LangChain内部SDK，也不复用 HTTP 报文日志钩子进行计量。
- **回调流程**：`on_chat_model_start` 按 LangChain 模型调用的 run_id 保存用户/会话快照，模型身份取工厂解析后的有效配置；`on_llm_end` 读取同次响应携带的完整原始计数和采集时间并写入，事件ID为 `lc:{run_id}`；`on_llm_error` 仅在本次回调可取得完整最终usage证据时写入。结束、异常均清理暂存状态。此 run_id 不是 `agent_runs` 的聊天 run_id，一轮聊天可对应多条模型用量。
- **计量粒度**：工具循环、子代理、压缩中的每次模型调用分别计量；流式chunk、SSE及历史回放不单独计量，HITL恢复只记录新调用。
- **数据校验**：输入/输出均须为非负整数，排除bool，供应商明确返回的0有效；缺失、null、非法或不能确认完整的用量跳过并记录日志，不把缺失字段补0，也不估算。`total_tokens` 不必存在，存在时也不替代输入/输出之和。只取原始计数这一种来源，不把归一化计数或多个累计usage块再相加。

现有 `StreamProcessor.last_usage` 和会话消息仅保存最近一次调用，无法覆盖中间调用，因此独立采集并保留现有输入框、SSE及会话usage语义。

#### 原始usage完整性

当前安装的LangChain适配器会把缺失的用量字段补0。例如供应商仅返回 `{"prompt_tokens":1000}`，仍可生成 `input_tokens=1000、output_tokens=0` 的 `usage_metadata`。因此，**归一化字段齐全、模型正常结束或出现finish_reason，都不能单独证明usage完整**。

| 路径 | 完整性依据与处理 |
| --- | --- |
| OpenAI兼容非流式 | 在 `ReasoningChatOpenAI._create_chat_result` 调用父类前提取原始 usage；校验两字段均显式存在且合法，并将计数/时间与该次结果绑定。`LLMResult.llm_output.token_usage` 可辅助核对，不能只检查归一化消息 |
| OpenAI兼容流式 | 在 `_convert_chunk_to_generation_chunk` 调父类前提取最终 usage 块；标准 `include_usage` 尾块可能 `choices=[]`，必须在现有无 choices 的提前返回之前处理；正文或只有finish_reason的块不构成完整依据 |
| SDK直调 | 校验 `completion.usage.prompt_tokens/completion_tokens` 均显式存在且合法，再统一写入；读取 SDK 原始对象的 `model_fields_set` 或 `model_dump(exclude_unset=True)`，避免默认值伪装成显式上报 |

适配层对 SDK 对象同样使用保留“字段是否上报”信息的读取方式。流式原始计数按单次调用保存**最终快照**，不能使用 LangChain 将多个 chunk 相加后的值：有些兼容网关会重复上报累计usage，重复相同快照不能使账本翻倍。当前支持标准完整尾块；仅分段计数、没有可确认最终快照的网关先跳过并记录缺口，不在本期增加猜测式协议适配。

完整性证据、最终计数和 `completed_at_ms` 属于单次响应的内部元数据，由适配层在字段补默认值前提取得到；不得写到共享模型实例的“最近一次usage”字段。在本次generation的 `generation_info.easy_agent_usage` 中使用**无index字段的快照对象列表**传递（非流式也用相同结构），结束时选最后一份完整最终快照。避免直接合并内含整数的嵌套字典，否则chunk归并可能累加计数和时间戳。已用锁定版本的 `ChatGenerationChunk` 合并验证：重复快照列表保留两份原值，选最后一份不会翻倍。实施时仍须测试真实callback分派、最终generation组装和SSE/会话消息契约，不能将内部字段作为对外usage新增字段。必要的临时状态按调用隔离，不跨调用拼接；callback只在结束时写一行，不按chunk写库。

发生中断或异常时，只有已收到且结束/错误回调可取到完整最终usage时才能入账；只有初始输入计数、部分输出或无法确认来源的归一化值时跳过。取消路径不保证框架会分派携带最终响应的错误回调，无法取得证据时接受缺口，不承诺所有取消均可入账。模型适配层涉及上游转换方法，依赖升级时必须运行对应契约测试。

### 2.2 用户归属与接入点

**目的：将每次调用记到正确用户，避免漏记或串账。** 在实际模型执行处使用 `usage_scope(user_id, session_id=None)`，通过ContextVar传递身份、退出时重置；不修改共享模型的用户字段。

真实user_id由API或服务层根据鉴权username、已校验会话用户或任务所有者，通过 `UserRepository` 查询得到；知识库可直接使用服务端鉴权产生的 `KnowledgePrincipal.user_id`。不接受客户端传入的统计用户，也不复用部分专家辅助方法中“查询失败则返回username”的兼容回退。查询失败或用户记录缺失时，本次采集跳过并记录错误，不阻断原模型业务。必须进入显式禁用的空scope，防止意外继承上层用户。`utils/usage_context.py` 只负责不可变身份快照和ContextVar，不导入数据库或上层服务。

| 场景 | 归属规则与接入位置（相对easy_agent/） |
| --- | --- |
| 聊天准备和专家预检 | 在 `services/agents/chat_turn.py` 完成会话归属校验后、调用 `experts.runtime.relevance_gate` 之前建立scope。即使预检拒答、不进入主聊天流，其真实调用仍入账 |
| 聊天、HITL恢复、子代理及自动摘要 | `services/streaming/orchestrator.py` 在实际消费 `chat_stream_generator` / `resume_stream_generator` 的任务内建立scope，覆盖模型执行和后处理。不能只在路由创建生成器时设置，生成器在后台任务迭代时才执行；`/stream/live` 只回放，不新增调用 |
| 手动压缩 | `services/sessions/compaction.py` 的 `_execute` 独立任务内按已校验会话建立scope，覆盖 `prepare_compaction`；原请求断开但任务继续时照常统计；同request_id已提交结果复用不再调用模型 |
| 专家生成/修改 | `api/expert_helpers.py:_generate_and_store`、`tools/expert_writer.py` 包住 `services/experts/service.py` 中实际生成调用；工具默认继承当前scope，独立入口须自行建立，不能重复安装callback |
| 知识问答 | `knowledges/api.py:ask` 使用可信principal包住 `_answer`；流式知识面板委托聊天链路，复用其scope，不叠加记录 |
| 公共补全 | `api/completion.py:chat_completion` 使用鉴权用户，包住实际 `llm.ainvoke`；`session_id=None`。指定模型失败回退全局模型时，账本跟随实际实例身份 |
| 提示词增强 | `api/prompt_enhancement.py` 根据鉴权username查询真实user_id，在 `await enhance_prompt(...)` 外建立scope；`services/prompt_enhancement.py` 在SDK返回后、`validate_completion`之前采集。现有服务没有用户参数，不能仅在服务内读取从未建立的scope |
| 定时任务 | `services/scheduler.py:_invoke_task_agent` 使用任务所有者及本次生成的会话ID，保留 `build_run_config(..., callbacks=[handler])` 的取消callback |
| 记忆更新线程 | `services/streaming/side_effects.py` 提交会话记忆、长期记忆任务时分别捕获不可变身份快照；在各自job内部建立scope，退出重置。`_submit_memory_job` 会串行排队且可能由前一任务完成回调提交，不能依赖线程池自动继承上下文 |

启动探测（`app.py`）、无用户归属的维护操作，以及 RAGFlow / MCP 等外部服务未向本应用返回的模型用量不计入个人统计。上下文估算（`agent/token_counting.py`、手动压缩的before/after）不调用模型，也不入账。

独立任务应显式传入身份快照并在执行体内建立scope。普通 `asyncio` 子任务、`run_blocking` 可继承当前ContextVar；LangChain跨线程callback分派是否保留上下文必须以锁定版本的实际分派测试验证。callback在start时冻结身份、end时按run_id读取，不依赖结束线程恰好仍有同一scope。

### 2.3 写入要求

提示词增强在SDK响应返回后、`validate_completion`之前捕获完整usage、模型身份、结束时间和唯一事件ID `sdk:{uuid}`；后续JSON解析、拒答检查或长度校验失败均不撤销已发生的消耗。每个响应只创建一次事件，失败收尾不能重新生成ID重复写入。

`completed_at_ms` 在适配层取得完整响应/最终usage块时捕获；SDK路径在 `await client.chat.completions.create(...)` 返回后立即捕获。这是应用观测到的完成时刻，不用供应商的请求创建时间，也不在可能延迟的callback线程入口取时间。`usage_date` 由该时间戳转换为上海日期；数据库等待跨过零点时仍归入原结束日期。

回调只装一次，保留原有callbacks及 `stream_usage=True`；按run_id管理的暂存状态需要线程安全，异常清理不能影响其他并发调用。同步callback使用 `run_inline=False`，不得在持有状态锁时等待数据库；SDK异步路径通过现有 `utils/blocking.py:run_blocking` 写库，避免阻塞事件循环。

增强服务现有 `asyncio.timeout` 只包住供应商调用及结果校验。账本写入在该业务超时块之外通过 `finally` 冲刷已捕获事件，保证解析失败也会写入，避免数据库锁等待被映射成“提示词增强超时”。写入异常独立捕获，不能覆盖原业务结果或异常；取消时沿用 `run_blocking` 等待已开始的写入完成的语义。

写入完成后返回，不建立异步写队列。通过 `db/providers.py` 新增的 `get_token_usage_repository()` 取得薄repository，不能在callback直接调用 `get_database()`，也不能由 `agent/token_usage.py` 反向导入 `services`。数据库写入失败仅记录event_id、模型标识与异常类型，不阻断用户回复，不记录正文或密钥。缺失身份、无完整usage、写库失败使用不同原因记录，便于排查漏接。供应商未上报、进程中断或写库失败产生的缺口不补算；同步确认写入意味着数据库等待仍会增加请求收尾耗时，本期接受该取舍。

### 2.4 模型身份与编译图缓存

callback固定持有工厂解析后的 `model_key` 和实际请求 `model_name`。显式模型键无效而工厂回退时，使用实际生效的active_model键，不保存无效请求键。

模型键解析须与 `resolve_llm_config` 共用规则：有效显式键优先，否则使用对应 `config.llm` 的active键；`model_name` 取实际请求配置，不能只取供应商返回的别名。专家预检按全局实例的active键、记忆按 `memory_model` 实例的键入账；回退到聊天实例时使用该实例固有身份。SDK增强的键固定取已通过 `_configured_model` 校验的 `config.prompt_enhancement.model`，缺失不能回退聊天键。

现有 `agent/graph_cache.py` 的模型指纹不包含配置键，两个键配置相同时可能命中同一编译图并复用首次创建的模型与callback，导致后续用量被记到第一个键。本期将**有效model_key加入编译图缓存键**：修改 `build_graph_key` 的显式参数及键材料，在 `agent/core.py` 传入，并递增 `GRAPH_CACHE_VERSION`。同一配置键仍可跨会话共享，不同配置键即使指向相同模型也分别缓存。

该键只增加模型配置身份，不包含user_id/session_id；用户归属仍走运行期scope。`SessionContext` 当前有username/session_id而没有真实user_id，不能直接将username当统计用户。模型适配层、摘要及辅助调用使用工厂提供的同一套采集规则，不在缓存命中后替换共享callback的身份。

### 2.5 失败、恢复和重试的计量边界

- 业务失败不等于模型未消耗：领域拒答、专家生成JSON校验失败、摘要成功后checkpoint提交失败，只要已取得完整usage都保留记录。手动压缩返回 `skipped` 且未调用摘要时不新增记录。
- 同一压缩request_id已提交时直接返回结果，不产生新用量；若上次摘要已调用但提交失败，重试实际再调一次模型，应新增一次用量，不能用request_id覆盖之前消耗。
- 应用层重试、HITL恢复和预检回退实际发起的新模型调用使用新的 LangChain run_id；HTTP SDK内部重试若未暴露usage，不估算隐藏尝试的消耗。
- SSE广播、`stream_events` 持久化、跨副本回放及 `agent_runs` 启动恢复只处理执行状态，不是usage来源。进程崩溃可能在取得响应与入库之间丢失记录，event_id幂等只能防重复，不能保证跨崩溃绝不漏记。

## 3. 存储：一张模型用量表

采用新增独立用量表的方案。现有消息记录只保存最后一次模型调用，且不能完整承载无会话的辅助调用；独立表便于逐调用核对，并能在删除会话后保留累计数据。

模型调用结束后，将用户、模型、结束时间及输入/输出Token写入项目自己的SQLite/MySQL，每次调用一行。新增表名为 `token_usage`，除session_id外均为NOT NULL；MySQL显式使用InnoDB，以支持§4.2的一致性快照。

例如上述调用的记录包含调用ID `lc:某个run_id`、当前用户与会话ID、模型 `default / deepseek-flash`、UTC结束时间及北京时间日期，输入/输出分别为1000和200。调用ID作为主键去重；查询时按用户、日期计算输入与输出之和，形成四张卡片和每日曲线。

| 字段 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| `event_id` | `VARCHAR(64) PRIMARY KEY` | 单次调用唯一ID，防重复 |
| `user_id` | `VARCHAR(255)` | 真实用户ID |
| `session_id` | `VARCHAR(255) NULL` | 可选会话标识，无删除级联 |
| `model_key` | `VARCHAR(128)` | 配置模型键快照 |
| `model_name` | `VARCHAR(255)` | 实际请求的模型名快照 |
| `completed_at_ms` | `BIGINT` | 调用结束UTC时间戳，毫秒 |
| `usage_date` | `VARCHAR(10)` | 结束时刻对应的上海日期，YYYY-MM-DD |
| `input_tokens` | `BIGINT` | 输入Token |
| `output_tokens` | `BIGINT` | 输出Token |

total查询时计算，不另存。模型按 `(model_key, model_name)` 区分，无需模型哈希、业务追踪、质量状态或额外拆分字段。MySQL 的event_id、模型键及名称使用大小写敏感的二进制排序规则，避免默认不区分大小写的collation将不同配置合并，保证与SQLite分组一致。session_id不设置外键，也不参加会话删除/归档、run清理或消息裁剪。

建立索引 `(user_id, completed_at_ms)` 和 `(user_id, usage_date)`。按event_id幂等插入：SQLite使用 `ON CONFLICT(event_id) DO NOTHING`，MySQL使用 `ON DUPLICATE KEY UPDATE event_id=event_id`；重复回调不累加，也不覆盖原记录。

在 `easy_agent/db/schema.py:_init_tables_full` 中直接调用幂等建表函数，加入 `EXPECTED_TABLES`，将实施时 `SCHEMA_VERSION` 递增（本次复核为16，若基线未变则升17）。这是核心账本表，不挂到会吞掉初始化异常的领域 `schema_registry`。当前 `db/migrations.py` 约定纯DDL仍走完整初始化加版本递增，不另加无必要的数据迁移。升级只增加表和索引，不扫描旧消息，不自动清理历史。SQL封装在新增 `TokenUsageRepository`，不向Database门面新增业务方法；同步补充 `db/providers.py` 和 `api/deps.py` 的repository provider。

## 4. 查询：一个接口返回卡片和趋势

接口每次同时返回两部分：**summary固定包含四张卡片，daily返回所选天数的趋势图数据。** `days`只控制daily，不限制summary的统计范围。

| 请求 | summary：始终返回 | daily：随参数变化 |
| --- | --- | --- |
| `GET /agent/usage?days=7` | 今天、近7日、近30日、总共 | 近7日每天的模型用量，共7个日期点 |
| `GET /agent/usage?days=30` | 今天、近7日、近30日、总共 | 近30日每天的模型用量，共30个日期点 |

因此不需要传 `days=1` 或 `days=all`：今天和累计已在summary中返回。切换图表范围时，重新请求同一个接口即可。

### 4.1 接口契约

新增 **`GET /agent/usage?days=7`**。

- 使用现有 `get_current_username` 鉴权，再查询用户记录取得真实user_id；SQL均带user_id条件，不接受客户端指定统计用户，也不回退为username查询。
- 查询侧找不到用户时按现有登录态失效语义返回401；用户查询/统计数据库故障返回503，不将身份缺失查询为另一用户或全局统计。API通过 `api/deps.py` 注入统计及用户repository，不读取 `repo.database` 拼SQL。
- days为**趋势图天数**，默认7，只允许7或30，其他值返回422；不影响四张卡片各自的时间范围。
- 使用同步路由适配现有数据库；返回Pydantic响应模型和 `Cache-Control: no-store`。
- 数据库查询失败返回503及“Token统计暂不可用，请重试”，不能返回空数据掩盖故障。

完整响应示例，对应§6固定测试数据：

```json
{
  "timezone": "Asia/Shanghai",
  "as_of": "2026-10-30T04:00:00.000Z",
  "days": 7,
  "summary": {
    "today": 1200,
    "last_7_days": 7000,
    "last_30_days": 17300,
    "all_time": 32000
  },
  "daily": {
    "dates": ["2026-10-24", "2026-10-25", "2026-10-26", "2026-10-27", "2026-10-28", "2026-10-29", "2026-10-30"],
    "totals": [3500, 0, 0, 0, 0, 2300, 1200],
    "series": [
      {
        "model_key": "default",
        "model_name": "deepseek-flash",
        "values": [3500, 0, 0, 0, 0, 0, 1200]
      },
      {
        "model_key": "secondary",
        "model_name": "model-b",
        "values": [0, 0, 0, 0, 0, 2300, 0]
      }
    ]
  }
}
```

### 4.2 聚合流程

1. 以一次as_of计算今天、近7日、近30日的上海零点，转换为UTC毫秒。
2. **计算summary，不使用days过滤**：对该用户查询时刻之前的记录做条件聚合，分别计算今天零点起、6天前零点起、29天前零点起及全部记录的 `input_tokens + output_tokens` 之和，得到四个固定字段。
3. **计算daily，使用days过滤**：days=7取6天前零点起，days=30取29天前零点起；按 `(usage_date, model_key, model_name)` 聚合，补齐连续7/30日，缺失值为0。
4. 每个正用量模型返回一条series，按窗口总量降序、model_key/model_name升序排列，不做Top N裁剪。
5. 每天totals等于所有series当天值之和。SQL SUM的NULL转0，MySQL Decimal转int；不将完整历史明细加载到Python。

两次聚合使用同一连接、同一显式读事务和as_of，保证一次响应内一致。repository一次完成summary与daily查询，不能由两个各自获取连接的方法拼接；as_of也不表示账本完整水位，更早完成但仍在等待写入的记录会在后续刷新才可见：

- SQLite：在现有 `get_connection()` 的锁内显式执行 `BEGIN`，再执行两次SELECT；普通SELECT和连接上下文不会自动建立所需读快照。
- MySQL：在尚未执行查询的连接上 `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ`，再以 `START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY` 建立InnoDB一致性快照；不能依赖服务器默认隔离级别。只设置当前事务，避免改变连接池后续请求的隔离配置；按现有连接池约定归还连接。
- 两次SELECT都使用同一个as_of上界；事务结束后提交或异常回滚。查询间并发写入不能使卡片与趋势取到不同快照，事务/查询失败按503处理。

空库四卡全0，dates仍为7/30个日期，totals全0、series为空。

### 6.4 测试要求与命令

功能实现时新增后端测试 `tests/agent/test_token_usage.py`、`tests/db/test_token_usage.py`、`tests/api/test_usage.py`，并补充现有模型适配、编译图缓存、专家预检、公共补全、手动压缩和提示词增强测试，覆盖：
