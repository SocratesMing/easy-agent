# Token 统计设计

> 项目：easy-agent｜状态：待实现｜日期：2026-10-30
> 参考：[Zcode Token 统计](../../Zcode-Token统计.md)、[当前项目架构](../architecture-current.md)。

## 1. 功能与统计规则

在“设置 → Token 统计”增加四张统计卡和一张每日趋势图，Vue2、Vue3 同步实现。

| 功能 | 规则 |
| --- | --- |
| 今天 | 北京时间今天00:00至查询时刻 |
| 七天 | 含今天的最近7个自然日 |
| 一个月 | 含今天的最近30个自然日，副标题“近30日” |
| 总共 | 功能启用以来已记录的全部用量 |
| 每日趋势图 | 默认近7日，可切换近30日；每个模型一条线，缺失日期补0 |
| 用户范围 | 按JWT鉴权得到username，再查询用户记录取得真实user_id |
| 总Token | `input_tokens + output_tokens`，思考和缓存Token不额外相加 |

统一使用 `Asia/Shanghai`，按模型调用结束时间归日，查询区间为 `[起点, 查询时刻)`。例如北京时间2026-10-30中午查询，近7日是10月24日至30日，近30日是10月1日至30日，分别恰好7/30个点。

只统计应用取得的完整真实usage，不估算未上报用量，不回填上线前历史。删除或归档会话不删除统计记录，重启后累计保持。
**数据链路：模型接口返回usage → 按调用记录到数据库 → SQL汇总 → 页面展示。**

## 2. 采集：每次模型调用结束记录一次

### 2.1 数据来源与采集方式

Token用量由模型供应商在API响应中返回。项目通过LangChain调用模型时，先确认供应商原始usage完整，再读取最终响应消息的 `usage_metadata`；提示词增强直接调用OpenAI SDK，校验并读取 `completion.usage` 中的 `prompt_tokens`、`completion_tokens`。例如一次LangChain响应携带：

```json
{
  "input_tokens": 1000,
  "output_tokens": 200,
  "total_tokens": 1200
}
```

应用将输入1000、输出200保存为一条调用记录，展示总量时计算得到1200。

**两条调用路径统一字段后写入同一张表，每次独立调用各存一行，查询时再汇总。** 字段映射如下：

| 调用路径 | 输入来源 | 输出来源 | 数据库目标字段 |
| --- | --- | --- | --- |
| LangChain | `usage_metadata.input_tokens` | `usage_metadata.output_tokens` | `input_tokens`、`output_tokens` |
| OpenAI SDK直调 | `completion.usage.prompt_tokens` | `completion.usage.completion_tokens` | `input_tokens`、`output_tokens` |

例如同一用户先增强提示词，再发送聊天，产生两次独立模型调用：

| 调用 | event_id示例 | input_tokens | output_tokens |
| --- | --- | ---: | ---: |
| 提示词增强（SDK直调） | `sdk:xxx` | 100 | 50 |
| 聊天模型（LangChain） | `lc:yyy` | 1000 | 200 |

两次调用分别写入 `token_usage`。在同一用户、同一统计窗口内，SQL累加两行的输入和输出：`(100 + 50) + (1000 + 200) = 1350 Token`。不需要将两行合并或覆盖为一行。

**采集规则：一次真实模型调用，只记录一次完整用量。**

- **接入点**：在 `easy_agent/agent/model.py:create_model` 安装一次callback；SDK适配仅用于绕过LangChain的直调，不拦截LangChain内部SDK，避免双重记录。
- **回调流程**：`on_chat_model_start` 按run_id保存用户/会话，模型身份取工厂解析后的有效配置；`on_llm_end` 校验完整性后读取最终usage并写入，事件ID为 `lc:{run_id}`；`on_llm_error` 仅在已取得供应商完整最终usage的证据时写入。结束后清理暂存状态。
- **计量粒度**：工具循环、子代理、压缩中的每次模型调用分别计量；流式chunk、SSE及历史回放不单独计量，HITL恢复只记录新调用。
- **数据校验**：输入/输出均须为非负整数，排除bool，供应商明确返回的0有效；缺失、null、非法或不能确认完整的用量跳过并记录日志，不把缺失字段补0，也不估算。仅在同次响应原始usage完整且无归一化usage时，允许按协议映射原始字段；每次调用只取一个数值来源。

现有 `StreamProcessor.last_usage` 和会话消息仅保存最近一次调用，无法覆盖中间调用，因此独立采集并保留现有输入框、SSE及会话usage语义。

#### 原始usage完整性

当前安装的LangChain适配器会把缺失的用量字段补0。例如供应商仅返回 `{"prompt_tokens":1000}`，仍可生成 `input_tokens=1000、output_tokens=0` 的 `usage_metadata`。因此，**归一化字段齐全、模型正常结束或出现finish_reason，都不能单独证明usage完整**。

| 路径 | 完整性依据与处理 |
| --- | --- |
| OpenAI兼容非流式 | 检查同次响应原始 `token_usage` 的 `prompt_tokens`、`completion_tokens` 均显式存在且合法；可从 `LLMResult.llm_output.token_usage` 读取，不能只检查归一化消息 |
| OpenAI兼容流式 | 在 `ReasoningChatOpenAI` 的原始chunk转换处检查供应商最终usage块，并保留完整性标记供结束callback读取；正文chunk和只有finish_reason的chunk不作为完整性依据 |
| Anthropic兼容 | 在模型适配层检查原始响应，或按同次流的协议事件组合确认最终输入/输出计数完整；必要时增加 `ChatAnthropic` 子类。缓存输入的组成按协议检查，数值沿用LangChain归一化结果，不重复加缓存Token |
| SDK直调 | 校验 `completion.usage.prompt_tokens/completion_tokens` 均显式存在且合法，再统一写入 |

完整性标记属于单次响应的内部元数据，由适配层在字段补默认值前检查原始数据得到；不得写到共享模型实例的“最近一次usage”字段。标记和数值必须对应同一次调用，不记录正文，不新增数据库字段。流式的协议状态按调用隔离，不跨调用拼接；callback只在结束时写一行，不按chunk写库。

发生中断或异常时，只有已收到完整最终usage才能入账；只有初始输入计数、部分输出或无法确认来源的归一化值时跳过。供应商协议不能提供完整证据时记录缺口，不靠框架补零入账。模型适配层涉及上游转换方法，依赖升级时必须运行对应契约测试。

### 2.2 用户归属与接入点

**目的：将每次调用记到正确用户，避免漏记或串账。** 在实际模型执行处使用 `usage_scope(user_id, session_id=None)`，通过ContextVar传递身份、退出时重置；不修改共享模型的用户字段。

真实user_id由API或服务层根据鉴权username、已校验会话用户或任务所有者查询得到，不接受客户端传入的统计用户。查询失败或用户记录缺失时，本次采集跳过并记录错误，不回退为username入账，不阻断原模型业务。`utils/usage_context.py` 只负责身份上下文，不导入数据库或上层服务。

| 场景 | 归属规则与接入位置（相对easy_agent/） |
| --- | --- |
| 聊天、恢复及压缩 | 使用已校验会话的用户；接入 `services/streaming/orchestrator.py`、`services/context_compaction.py`，子代理与自动摘要继承 |
| 专家、知识问答 | 使用鉴权用户或继承当前scope；接入 `services/expert_runtime.py`、`api/expert_helpers.py`、`tools/expert_writer.py`、`knowledges/api.py` |
| 提示词增强 | `api/prompt_enhancement.py` 根据鉴权username查询真实user_id，在 `await enhance_prompt(...)` 外建立scope；`services/prompt_enhancement.py` 在该scope内完成SDK采集。现有服务签名没有用户参数，不能仅在服务内读一个从未建立的scope |
| 定时任务 | `services/scheduler.py` 使用任务所有者，保留原取消callback |
| 记忆更新线程 | `services/streaming/side_effects.py` 提交的两个线程分别携带用户身份，在线程内建立scope |

启动探测、无鉴权用户的公共补全，以及外部服务未提供的模型用量不计入个人统计。

### 2.3 写入要求

提示词增强在SDK响应返回后、`parse_result`之前写入，事件ID为 `sdk:{uuid}`；后续JSON解析失败不影响已记录用量。

`completed_at_ms` 在结束callback入口捕获；SDK路径在 `await client.chat.completions.create(...)` 返回后立即捕获。`usage_date` 由该时间戳转换为上海日期，之后传给repository；不在取得数据库连接、等待锁或INSERT时重新取时间。数据库等待跨过零点时仍归入原结束日期。

回调只装一次，保留原有callbacks及 `stream_usage=True`；按run_id管理的暂存状态需要线程安全。同步callback使用 `run_inline=False`；SDK异步路径通过现有 `utils/blocking.py:run_blocking` 写库，避免阻塞事件循环。

写入完成后返回，不建立异步写队列。数据库写入失败仅记录event_id、模型标识与异常类型，不阻断用户回复，不记录正文或密钥。供应商未上报、进程中断或写库失败产生的缺口不补算。

### 2.4 模型身份与编译图缓存

callback固定持有工厂解析后的 `model_key` 和实际请求 `model_name`。显式模型键无效而工厂回退时，使用实际生效的active_model键，不保存无效请求键。

现有 `agent/graph_cache.py` 的模型指纹不包含配置键，两个键配置相同时可能命中同一编译图并复用首次创建的模型与callback，导致后续用量被记到第一个键。本期将**有效model_key加入编译图缓存键**：修改 `build_graph_key` 的显式参数及键材料，在 `agent/core.py` 传入，并递增 `GRAPH_CACHE_VERSION`。同一配置键仍可跨会话共享，不同配置键即使指向相同模型也分别缓存。

该键只增加模型配置身份，不包含user_id/session_id；用户归属仍走运行期scope。模型适配层、摘要及辅助调用使用工厂提供的同一套采集规则，不在缓存命中后替换共享callback的身份。

## 3. 存储：一张模型用量表

采用新增独立用量表的方案。现有消息记录只保存最后一次模型调用，且不能完整承载无会话的辅助调用；独立表便于逐调用核对，并能在删除会话后保留累计数据。

模型调用结束后，将用户、模型、结束时间及输入/输出Token写入项目自己的SQLite/MySQL，每次调用一行。新增表名为 `token_usage`，除session_id外均为NOT NULL；MySQL显式使用InnoDB，以支持§4.2的一致性快照。

例如上述调用的记录包含调用ID `lc:某个run_id`、当前用户与会话ID、模型 `default / deepseek-flash`、UTC结束时间及北京时间日期，输入/输出分别为1000和200。调用ID作为主键去重；查询时按用户、日期计算输入与输出之和，形成四张卡片和每日曲线。

| 字段 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| `event_id` | `VARCHAR(64) PRIMARY KEY` | 单次调用唯一ID，防重复 |
| `user_id` | `VARCHAR(255)` | 真实用户ID |
| `session_id` | `VARCHAR(255) NULL` | 可选会话标识，无删除级联 |
| `model_key` | `VARCHAR(128)` | 配置模型键快照 |
| `model_name` | `VARCHAR(255)` | 实际请求的模型名快照 |
| `completed_at_ms` | `BIGINT` | 调用结束UTC时间戳，毫秒 |
| `usage_date` | `VARCHAR(10)` | 结束时刻对应的上海日期，YYYY-MM-DD |
| `input_tokens` | `BIGINT` | 输入Token |
| `output_tokens` | `BIGINT` | 输出Token |

total查询时计算，不另存。模型按 `(model_key, model_name)` 区分，无需模型哈希、业务追踪、质量状态或额外拆分字段。

建立索引 `(user_id, completed_at_ms)` 和 `(user_id, usage_date)`。按event_id幂等插入：SQLite使用 `ON CONFLICT(event_id) DO NOTHING`，MySQL使用 `ON DUPLICATE KEY UPDATE event_id=event_id`；重复回调不累加，也不覆盖原记录。

在 `easy_agent/db/schema.py` 的完整初始化中建表，加入 `EXPECTED_TABLES`，将实施时 `SCHEMA_VERSION` 递增。升级只增加表和索引，不扫描旧消息，不自动清理历史。SQL封装在新增repository，不向Database门面新增业务方法。

## 4. 查询：一个接口返回卡片和趋势

接口每次同时返回两部分：**summary固定包含四张卡片，daily返回所选天数的趋势图数据。** `days`只控制daily，不限制summary的统计范围。

| 请求 | summary：始终返回 | daily：随参数变化 |
| --- | --- | --- |
| `GET /agent/usage?days=7` | 今天、近7日、近30日、总共 | 近7日每天的模型用量，共7个日期点 |
| `GET /agent/usage?days=30` | 今天、近7日、近30日、总共 | 近30日每天的模型用量，共30个日期点 |

因此不需要传 `days=1` 或 `days=all`：今天和累计已在summary中返回。切换图表范围时，重新请求同一个接口即可。

### 4.1 接口契约

新增 **`GET /agent/usage?days=7`**。

- 使用现有 `get_current_username` 鉴权，再查询用户记录取得真实user_id；SQL均带user_id条件，不接受客户端指定统计用户，也不回退为username查询。
- days为**趋势图天数**，默认7，只允许7或30，其他值返回422；不影响四张卡片各自的时间范围。
- 使用同步路由适配现有数据库；返回Pydantic响应模型和 `Cache-Control: no-store`。
- 数据库查询失败返回503及“Token统计暂不可用，请重试”，不能返回空数据掩盖故障。

完整响应示例，对应§6固定测试数据：

```json
{
  "timezone": "Asia/Shanghai",
  "as_of": "2026-10-30T04:00:00.000Z",
  "days": 7,
  "summary": {
    "today": 1200,
    "last_7_days": 7000,
    "last_30_days": 17300,
    "all_time": 32000
  },
  "daily": {
    "dates": ["2026-10-24", "2026-10-25", "2026-10-26", "2026-10-27", "2026-10-28", "2026-10-29", "2026-10-30"],
    "totals": [3500, 0, 0, 0, 0, 2300, 1200],
    "series": [
      {
        "model_key": "default",
        "model_name": "deepseek-flash",
        "values": [3500, 0, 0, 0, 0, 0, 1200]
      },
      {
        "model_key": "secondary",
        "model_name": "model-b",
        "values": [0, 0, 0, 0, 0, 2300, 0]
      }
    ]
  }
}
```

### 4.2 聚合流程

1. 以一次as_of计算今天、近7日、近30日的上海零点，转换为UTC毫秒。
2. **计算summary，不使用days过滤**：对该用户查询时刻之前的记录做条件聚合，分别计算今天零点起、6天前零点起、29天前零点起及全部记录的 `input_tokens + output_tokens` 之和，得到四个固定字段。
3. **计算daily，使用days过滤**：days=7取6天前零点起，days=30取29天前零点起；按 `(usage_date, model_key, model_name)` 聚合，补齐连续7/30日，缺失值为0。
4. 每个正用量模型返回一条series，按窗口总量降序、model_key/model_name升序排列，不做Top N裁剪。
5. 每天totals等于所有series当天值之和。SQL SUM的NULL转0，MySQL Decimal转int；不将完整历史明细加载到Python。

两次聚合使用同一连接、同一显式读事务和as_of，保证一次响应内一致。repository一次完成summary与daily查询，不能由两个各自获取连接的方法拼接：

- SQLite：在现有 `get_connection()` 的锁内显式执行 `BEGIN`，再执行两次SELECT；普通SELECT和连接上下文不会自动建立所需读快照。
- MySQL：本次查询事务明确使用 `REPEATABLE READ`，以 `START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY` 建立InnoDB一致性快照；不能依赖服务器默认隔离级别。只设置当前事务，避免改变连接池后续请求的隔离配置。
- 两次SELECT都使用同一个as_of上界；事务结束后提交或异常回滚。查询间并发写入不能使卡片与趋势取到不同快照，事务/查询失败按503处理。

空库四卡全0，dates仍为7/30个日期，totals全0、series为空。

| --- | --- |
| 数据请求 | 进入页签请求days=7；切换和刷新请求当前范围，统一更新卡片与趋势。切换days不改变四卡的窗口定义 |

| 布局与生命周期 | 桌面四卡一行、窄屏两列；适配主题和resize，范围更新时dispose后重建图表，卸载释放实例 |

### 6.2 固定数据验收

固定查询时刻为 `2026-10-30T04:00:00.000Z`。以下为不同event_id的完整调用，日期均为上海日期；10月30日记录在11:00结束，其他日期在12:00结束。模型A对应default/deepseek-flash，B对应secondary/model-b。

| 日期 | 用户 | 模型 | input | output |
| --- | --- | --- | ---: | ---: |
| 2026-10-30 | Alice | A | 1000 | 200 |
| 2026-10-29 | Alice | B | 2000 | 300 |
| 2026-10-24 | Alice | A | 3000 | 500 |
| 2026-10-23 | Alice | A | 4000 | 600 |
| 2026-10-01 | Alice | B | 5000 | 700 |
| 2026-09-30 | Alice | A | 6000 | 800 |
| 2026-08-31 | Alice | A | 7000 | 900 |
| 2026-10-30 | Bob | A | 90000 | 10000 |

### 6.3 准确性验证

从采集、聚合和展示三个环节验证：

| 验证环节 | 方法与通过标准 |
| --- | --- |
| 采集准确 | 假模型固定返回input=1000、output=200，数据库恰好新增一行且数值一致；相同event_id重复处理仍只有一行。验证多步调用、子代理、流式输出及HITL恢复：真实调用各自入账，chunk及回放不重复计入 |
| 聚合准确 | 写入§6.2固定数据，Alice四卡应为1200、7000、17300、32000；验证7/30日边界、缺失日期补0、用户隔离，以及每日模型合计 |
| 展示准确 | 同一用户、范围和查询时刻，数据库求和=接口结果=页面精确值。近7/30日卡片分别等于对应趋势全部日期totals之和，totals等于各模型逐日之和；切换范围、重启服务、删除会话后仍符合统计规则 |

联调再抽查真实模型响应，将其usage与对应event_id的数据库记录逐项比较。对比在测试/调试环境中进行，不将完整模型响应或密钥写入业务日志。页面使用万/亿缩写时，按悬浮显示的精确数值核对。

准确性目标是确保**已上报且成功入库的用量在采集、存储、聚合和展示中保持一致**。供应商未上报、进程中断或写库失败时可能存在缺口，因此页面表示“已记录用量”，不承诺与供应商账单完全一致。
