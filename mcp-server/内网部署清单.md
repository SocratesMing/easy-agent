# mcp-server 内网部署清单

> 按顺序执行，每步都有**验证点**，通过再进下一步。
> 标 ⚠️ 的是实际部署中踩过的坑，值得停下来确认。
>
> 涉及两个服务：
> - **主应用** easy-agent（默认 8000 端口）
> - **mcp-server** 本子项目（本项目统一用 **8174** 端口）

---

## 0. 前置条件

| 项 | 要求 |
|---|---|
| Python | 3.11+（本项目在 3.12 上验证） |
| uv | 推荐；没有也可以用 pip（见第 2 节方案 B） |
| MySQL | 主应用与 mcp-server **共用同一个库** |
| 网络 | mcp-server 需被主应用访问（同机则回环即可） |

## 1. 复制代码

### 1.1 打包清单

以**目录**为单位列，比逐个文件不容易漏。

#### 必带

| 路径 | 备注 |
|---|---|
| `easy_mcp_server/` | 整个目录（`app.py` / `db.py` / `keys.py` / `registry.py` / `contract.py` …） |
| └ `querykit/` | 表可见性策略、只读 SQL 网关、连接池 |
| └ `businesses/strategyqa/` | 策略问数业务包 |
| └ `businesses/investment_research/` | 投资研究业务包（4 个场景 · 14 张表） |
| `tests/` | 想在内网跑测试就带 |
| `scripts/init_keys.py` | 运维必需：建表 / 造 Key |
| `scripts/retire_business.py` | 运维必需：下线业务（见第 10 节） |
| `pyproject.toml` | 必须 |
| `.env.example` | 内网复制成 `.env` 后填值（见第 3 节） |
| `README.md`、`内网部署清单.md`、`iData-*.md` | 文档 |
| `docs/MCP_docs/`（**仓库根目录**下，不在 mcp-server 里） | 四个场景的 SQL 清单，业务口径参考 |

#### 按需

| 路径 | 说明 |
|---|---|
| `businesses/fxbar/` | 不需要外汇 K 线就不带 |
| `tests/test_fxbar.py` | **随 fxbar** ⚠️ 不带 fxbar 却带它 → pytest 收集报错 |
| `scripts/seed_fxbar_demo.py`、`scripts/smoke_fxbar.py` | 同上，一起排除 |
| `scripts/seed_idata_demo.py`、`scripts/smoke_idata.py` | 连库造演示数据 / 冒烟验证，可选 |
| `uv.lock` | 见 1.3 |

#### 绝不要带

| 路径 | 原因 |
|---|---|
| **`.venv/`** ⚠️ | 写死外网机器的 Python 绝对路径，带过去必然报 **`No Python at C:\...`** |
| **`.env`** ⚠️ | 内网库地址/密码不同，必须手工重建 |
| `__pycache__/`、`.pytest_cache/` | 无意义 |
| `logs/`、`workspace/` | 运行时产物 |
| `*.tar.gz` | 打包产物本身，别套娃 |

### 1.2 打包命令

⚠️ **别用 `git archive`**：它只打**已提交**的内容，未提交的改动会静默漏掉。用 `tar`：

```powershell
cd mcp-server
tar -czf ..\mcp-server-full.tar.gz `
    --exclude=.venv --exclude=__pycache__ --exclude=.pytest_cache `
    --exclude=.env --exclude=logs --exclude="*.tar.gz" .
```

不带 fxbar 时追加这几条 `--exclude`：

```powershell
    --exclude="./easy_mcp_server/businesses/fxbar" `
    --exclude="./tests/test_fxbar.py" `
    --exclude="./scripts/seed_fxbar_demo.py" --exclude="./scripts/smoke_fxbar.py"
```

> Windows 自带的 `tar` 打**中文文件名**（`内网部署清单.md` 等）解压后可能乱码。
> 这几个 md 建议单独拷，或改用 7-Zip（默认按 UTF-8 存名）。

### 1.3 `uv.lock` 的取舍 ⚠️

| 情况 | 做法 |
|---|---|
| 内网已有能跑通的 lock | **不要覆盖**，直接跳过 |
| 内网 lock 太旧 / 报版本冲突 | 用外网这份**覆盖**，再 `uv sync --frozen` |

⚠️ **两份 lock 不能混着用**。uv 的更新策略是「基于当前 lock 做最小变更」，
拿一份旧 lock 去解析新约束，会撞出莫名其妙的冲突（典型症状：
`uvicorn<0.30.0` 与 `mcp>=1.27.0` 互斥，而 `mcp` 其实压根没限制 uvicorn 上限）。

内网若为了指向镜像源重新生成过 lock，这份 **不要提交回外网仓库**。

## 2. 安装依赖

### 方案 A：uv + 内网镜像（推荐）

```bash
# 1) 装 uv（内网有 PyPI 镜像时）
pip install uv -i http://<内网镜像>/simple --trusted-host <镜像主机>   # http 镜像才需要 --trusted-host

# 2) 让 uv 认内网镜像（重开终端后生效）
export UV_INDEX_URL=http://<内网镜像>/simple
export UV_INSECURE_HOST=<镜像主机>        # 仅 http 镜像需要

# 3) 重建环境
cd mcp-server
uv sync
```

⚠️ **`uv.lock` 里记的是外网镜像源**（如 `pypi.tuna.tsinghua.edu.cn`），内网连不上。
若 `uv sync` 报 lockfile 与索引不一致：

```bash
uv lock --index-url http://<内网镜像>/simple
uv sync
```

> 这会把内网的 `uv.lock` 改写成指向内网镜像。此后这份 lock **不要提交回外网仓库**。

### 方案 B：不用 uv（降级）

外网导出精确版本清单（**保住 `--no-dev`** 会排除测试依赖，想跑测试就去掉它）：

```bash
cd mcp-server
uv export --frozen --no-dev --no-emit-project -o requirements.txt
```

内网：

```bash
python -m venv .venv
.venv/bin/pip install -r requirements.txt -i http://<内网镜像>/simple --trusted-host <镜像主机>
# Windows: .venv\Scripts\python -m pip install ...
```

之后所有 `uv run xxx` 换成 `.venv/bin/python -m xxx`。

### 本项目的依赖情况

| 业务 | 是否需要新依赖 |
|---|---|
| `strategyqa` / `fxbar` / `investment_research` | **都不需要**，只用 `mcp` / `fastapi` / `uvicorn` / `pymysql` / `DBUtils` / `anyio` |

所以新增业务后**不需要重新 sync**。

## 3. 配置 `.env`

从模板复制后**只改值**（不要新增重复的变量名——同名变量只有第一个生效）：

```bash
cp .env.example .env
```

### 必改

| 变量 | 说明 |
|---|---|
| `MYSQL_HOST` / `MYSQL_PORT` | 内网库地址 |
| `MYSQL_USER` / `MYSQL_PASSWORD` | 账号（建议只读，见第 4 节） |
| `MYSQL_DATABASE` | **必须与主应用 `config.yaml` 的 `database.mysql.database` 一致** ⚠️ |
| `MCP_ALLOWED_HOSTS` | 用域名/IP 访问时必须配（见下） |

### 按需改

| 变量 | 缺省 | 说明 |
|---|---|---|
| `MCP_KEY_CACHE_TTL` | 60 | Key 校验缓存秒数；吊销后最多这么久才失效 |
| `QUERYKIT_POOL_SIZE` | 5 | 连接池上限兼预热数；**多进程时实际连接数 = 进程数 × 该值** |
| `QUERYKIT_MAX_ROWS` | 500 | 单次查询返回行数上限 |
| `QUERYKIT_TIMEOUT_MS` | 10000 | 单次查询超时（毫秒） |
| `STRATEGY_TABLE` | `fmut2_strategy_manage` | 策略表名 |
| `FX_SCHEMA` | 空 | 外汇表所在库（同库则留空） |
| `FX_CHANNELS` | `BEST,FXALL` | 缺省渠道 |
| `FX_DEFAULT_WINDOW_HOURS` | 24 | K 线默认回溯窗口 |
| `FX_MAX_WINDOW_DAYS` | 31 | 显式时间范围上限（超出自动收敛） |
| `IDATA_SCHEMA` | 空 | 场景1 iData 四张表所在库（同库则留空） |
| `FORECAST_SCHEMA` | 空 | 场景2 宏观预测六张表所在库（同库则留空） |
| `RATES_SCHEMA` | 空 | 场景3 利率择时两张表所在库（同库则留空） |
| `WEEKLY_RESEARCH_SCHEMA` | 空 | 场景4 研报观点两张表所在库（同库则留空） |

> 四个场景共 14 张表。若分散在不同 database，对应的 `*_SCHEMA` 必须分别填；
> 全留空则统一用 `MYSQL_DATABASE`。各场景的表名白名单代码里缺省已配全，
> 一般无需设置 `*_ALLOWED_TABLES`。

### MCP_ALLOWED_HOSTS ⚠️

FastMCP 默认只放行 `127.0.0.1/localhost`。**通过域名或反向代理访问时，不配这个会全部返回 421**，
而且报错完全不提配置：

```bash
MCP_ALLOWED_HOSTS=mcp.internal,mcp.internal:8174
MCP_ALLOWED_ORIGINS=http://mcp.internal:8174
```

`host:*` 只匹配**带端口**的 Host，两种写法都要列。走 `127.0.0.1` 访问则不需要配。

## 4. 数据库

### 4.1 两边的库必须一致 ⚠️

```
主应用 ──写 mcp_api_keys──▶ 同一个 MySQL 库 ◀──只读校验── mcp-server
```

不一致的症状是「主应用签发了 Key，MCP 一律 401」，**没有任何报错指向配置**。

启动后第一件事就是核对这行日志：

```
[mcp-server] MySQL 目标: <host>:<port>/<database>
```

### 4.2 需要的两张表

| 表 | 谁建 | 说明 |
|---|---|---|
| `mcp_businesses` | **mcp-server 启动时自愈建表**（`CREATE TABLE IF NOT EXISTS`）；主应用 `init_tables` 也会建 | 业务清单，主应用读它渲染设置页下拉 |
| `mcp_api_keys` | **主应用 `init_tables`**（或 `scripts/init_keys.py` 自举） | Key 校验，mcp-server 只读 |

⚠️ **如果 mcp-server 用的是只读账号**，自愈建表会失败——而 `publish()` **只告警不阻断**，
服务照常启动，但注册表为空 → 主应用回退内置兜底清单 → 设置页看不到新业务。

三个处理方式任选：

1. 确保主应用启动过一次（它的 `init_tables` 会建这两张表）
2. 临时给 mcp-server 账号 `GRANT CREATE ON <库>.*`，建完收回
3. 手工执行一次：

```sql
CREATE TABLE IF NOT EXISTS mcp_businesses (
    name       VARCHAR(64) PRIMARY KEY,
    created_at VARCHAR(50) NOT NULL,
    updated_at VARCHAR(50) NOT NULL
);
```

### 4.3 账号权限建议

```sql
CREATE USER 'mcp_ro'@'%' IDENTIFIED BY '<密码>';
GRANT SELECT ON <库>.* TO 'mcp_ro'@'%';
```

只读即可（所有工具都是 SELECT）；但注意上面 4.2 的建表问题。

## 5. 启动与验证

```bash
cd mcp-server
uv run uvicorn easy_mcp_server.main:app --host 0.0.0.0 --port 8174 \
    --timeout-graceful-shutdown 5
```

> `--host 0.0.0.0`：跨机器访问必须；只监听 `127.0.0.1` 时别的机器连不上。
> `--timeout-graceful-shutdown 5`：不加的话 Ctrl+C 会卡在 "Shutting down"。

### 启动日志的三个检查点

```
[mcp-server] MySQL 目标: <host>:<port>/<database>        ← 库对不对
[mcp-server] 已挂载业务: <业务名> -> /mcp/<业务名>/         ← 业务包被扫到了吗
[mcp-server] 业务注册表已更新: <业务名列表>                 ← 注册表写入成功吗（失败会打警告）
```

### 接口验证

```bash
curl http://127.0.0.1:8174/health      # {"status":"ok","businesses":[...]}
curl http://127.0.0.1:8174/manifest    # 业务清单 + URL（免鉴权）
```

## 6. 主应用侧

### 6.1 数据库配置

`easy_agent/config/config.yaml` → `database.mysql`，**库名必须与 mcp-server 的 `MYSQL_DATABASE` 相同**。

### 6.2 MCP 市场配置（手工建，不入库）⚠️

`easy_agent/config/mcp.json` 被 `.gitignore` 排除，**每个环境各维护一份**，
不建的话设置页「从市场添加」会显示"暂无公共 MCP 服务"：

```bash
cp easy_agent/config/mcp.json.example easy_agent/config/mcp.json
```

内容示例（三个业务都列上）：

```json
{
  "servers": {
    "strategyqa": {
      "transport": "streamable_http",
      "url": "http://<mcp-server 地址>:8174/mcp/strategyqa/",
      "headers": { "Authorization": "Bearer <在设置页生成的 Key>" }
    },
    "fxbar": {
      "transport": "streamable_http",
      "url": "http://<mcp-server 地址>:8174/mcp/fxbar/",
      "headers": { "Authorization": "Bearer <在设置页生成的 Key>" }
    },
    "investment_research": {
      "transport": "streamable_http",
      "url": "http://<mcp-server 地址>:8174/mcp/investment_research/",
      "headers": { "Authorization": "Bearer <在设置页生成的 Key>" }
    }
  }
}
```

> **URL 尾斜杠不能省**：主应用靠 `/mcp/<业务>/` 识别业务名并自动注入 Key，
> 少了尾斜杠连业务名都解析不出来。

### 6.3 业务下拉的来源

设置页的业务下拉**不是硬编码**，而是：

```
mcp-server 启动 publish → mcp_businesses 表 → supported_businesses() → GET /agent/settings/mcp/api-keys → 下拉
```

代码位置：`easy_agent/services/mcp_api_keys.py`（读表，60s 缓存，读不到时回退兜底常量
`SUPPORTED_BUSINESSES`）。**所以新增业务不用改主应用**。

⚠️ 表里有但界面没有 → 多半是那 60s 缓存（等一分钟或重启主应用）。

## 7. 三个业务的上线前核对

### strategyqa（策略问数）

| 项 | 值 |
|---|---|
| 表 | `fmut2_strategy_manage` |
| 关键配置 | `STRATEGY_TABLE` |
| 权限模型 | **行级隔离**：只返回 `AUTHOR = 当前登录账号` 的策略 |
| 前提 ⚠️ | 主应用的用户名必须与表里的 `AUTHOR` 一致（统一账号体系），否则结果永远为空 |

### fxbar（外汇 K 线）

| 项 | 值 |
|---|---|
| 表 | `HSDC_HDS2_BAR_FX` |
| 关键配置 | `FX_TABLE`、`FX_SCHEMA`、`FX_CHANNELS` |
| 设计要点 | 大表保护：缺省只查最近 24h，超 31 天自动收敛 |
| 上线前确认 | ① 表在哪个库（填 `FX_SCHEMA`）② `CHANNEL` 实际取值（`BEST`/`FXALL` 对不对）③ 合约代码形态（`EURUSD` 还是别的） |

### investment_research（投资研究 · 4 个场景 14 张表）

四个场景挂在**同一个业务包**下（同一个 MCP 地址 `/mcp/investment_research/`），
每个场景一个领域模块 + 一个自己的 `describe_*_schema` 工具；表名常量在各模块顶部。

| 场景 | 模块 | 表（张数） | 表所在库 |
|---|---|---|---|
| ① iData 数据分析看板 | `idata.py` | `fmqt_bond_exec_part_data`、`fmqt_bond_trade_counterpart_analysis`、`fmqt_bond_lending_analysis`、`fmqt_idata_llm_analysis`（4） | `IDATA_SCHEMA` |
| ② 国内宏观经济指标预测 | `domestic_macro.py` | `fmqt_forecast_report_meta`、`fmqt_forecast_indicator`、`fmqt_forecast_prediction`、`fmqt_forecast_feature_contribution`、`fmqt_forecast_selected_feature`、`fmqt_forecast_analysis`（6） | `FORECAST_SCHEMA` |
| ③ 利率择时（只读已存结果） | `rates_timing.py` | `fmqt_predictions_rates`、`fmqt_prediction_runs_rates`（2） | `RATES_SCHEMA` |
| ④ 研报观点矩阵与宏观预测 | `weekly_research.py` | `weekly_analyzer_data`、`weekly_macro_data`（2） | `WEEKLY_RESEARCH_SCHEMA` |

**上线前确认**：

1. **14 张表是否都在**（上表逐个与业务库核对过）
2. **分库**：四个场景的表若不在同一个 database，对应的 `*_SCHEMA` 必须填；全留空则都用 `MYSQL_DATABASE`
3. **表名易错点** ⚠️：业务方 SQL 清单里把周报观点表写成 `weekly_data`，**实际库中是 `weekly_analyzer_data`**（代码已修正，并有测试钉住）
4. **iData 场景口径**：金额统一亿元（`_yi` 后缀），日期 `YYYYMMDD` 且缺省取最新交易日；
   字段名重点看 `STATISTIC_SUBDETAIL_NAME` / `RELATED_STATISTIC_SUBDETAIL_NAME`；
   合计行口径（`include_total` 切换后金额是否合理，**混用会翻倍**）；借贷余额 `STATISTIC_AMT_TYPE='19'`

> 表名/字段名若有出入，改动集中在各场景模块顶部的 `TABLES` 常量区，
> 改完 `uv run pytest tests/ -q` 就能验证，不用连库。
> 结构探索白名单缺省已汇总四个场景全部 14 张表（`IDATA_ALLOWED_TABLES` 可整体覆盖）。

## 8. 端到端验证

1. **签发 Key**：设置页 → MCP → 选业务 → 生成（明文只显示一次，库里只存 sha256）
2. **添加服务**：从市场添加（本业务会自动注入 Key，无需手工粘贴）
3. **问一句**，验证工具被调用：
   - strategyqa → "我有哪些策略"
   - fxbar → "EURUSD 最近一天的一小时 K 线"
   - investment_research → 四个场景各问一句：
     - iData → "今天各机构净买入情况"
     - 宏观预测 → "最新一期宏观预测报告有哪些指标"
     - 利率择时 → "最近的利率择时信号"
     - 研报观点 → "上周研报观点对债券的看法"
4. **看日志**：`MCP tools loaded (...): N tool(s)`，失败会有 `MCP server 加载失败，已跳过 | <名字>: <原因>`

### 手动造一把 Key（排障用）

明文必须是 `mcp_` 开头，哈希算**整串**（不含 `Bearer `）：

```sql
INSERT INTO mcp_api_keys (username, business, key_hash, created_at, updated_at, revoked)
VALUES ('someone', 'fxbar', SHA2('mcp_自定义明文', 256), NOW(), NOW(), 0)
ON DUPLICATE KEY UPDATE key_hash = VALUES(key_hash), revoked = 0;
```

客户端用 `Authorization: Bearer mcp_自定义明文`。

- `revoked` 必须为 0
- 表上有 `UNIQUE(username, business)`：每用户每业务只有一把有效 Key，重签即覆盖
- **新 Key 立即生效；吊销最多延迟 `MCP_KEY_CACHE_TTL`（60s）**

## 9. 故障排查

| 症状 | 最可能的原因 | 处理 |
|---|---|---|
| `No Python at C:\...` | 复制了外网的 `.venv` | 删掉 `.venv` 重新 `uv sync` |
| `uv` 不是内部或外部命令 | 内网没装 uv | 装 uv，或用方案 B（pip） |
| `uv sync` 报依赖冲突 / 版本过期 | lock 与索引不一致 | `uv lock --index-url <内网镜像>` 后重新 sync |
| 所有请求 **421** | `MCP_ALLOWED_HOSTS` 没配 | 按第 3 节配置（两种写法都列） |
| 所有请求 **401** | 两边库不一致 / `mcp_api_keys` 缺失 | 核对启动日志的 `MySQL 目标`；确认表存在 |
| 设置页看不到新业务 | 注册表没写 / 主应用 60s 缓存 | 查 `SELECT name FROM mcp_businesses`；等 1 分钟或重启主应用 |
| 市场列表是空的 | `easy_agent/config/mcp.json` 不存在 | 按 6.2 创建 |
| 日志只有部分业务 | 业务包没放对位置 | 必须在 `easy_mcp_server/businesses/<name>/`，且有 `__init__.py` 暴露 `build()` |
| 添加服务时报"已添加" | 用户配置里已有同名条目 | 先删除再添加（改市场配置不会同步给已添加的用户） |
| 服务连不上（跨机器） | 只监听了 `127.0.0.1` | 改 `--host 0.0.0.0` |
| Ctrl+C 卡在 "Shutting down" | 没加超时参数 | 加 `--timeout-graceful-shutdown 5`，或再按一次 Ctrl+C |

## 10. 日常运维

### 新增业务

1. 在 `easy_mcp_server/businesses/` 下新建业务包（暴露 `build() -> FastMCP`）
2. 重启 mcp-server → 注册表自动更新
3. **主应用零改动**，设置页下拉自动出现

### 删除业务

1. 删掉业务包目录
2. 重启 mcp-server，确认 `/health` 里已无该业务
3. **必须**清理共享库残留（`registry.publish()` 只 upsert、从不删除）：

```bash
uv run python -m scripts.retire_business <业务名>            # 预览
uv run python -m scripts.retire_business <业务名> --apply    # 执行
```

不清理的话，设置页会一直显示已下线的业务，用户还能对它签发永远用不了的 Key。

### 吊销某个用户的 Key

```sql
UPDATE mcp_api_keys SET revoked = 1 WHERE username = '<用户>' AND business = '<业务>';
```

注意 60s 缓存延迟；用户的 `mcp.json` 里那份明文也建议删掉。

### 造本地测试 Key

```bash
uv run python -m scripts.init_keys                       # 建表 + 默认 demo key
uv run python -m scripts.init_keys -u alice -b fxbar     # 给指定用户/业务签发
```
