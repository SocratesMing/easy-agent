# mcp-server 新增 MCP 场景迁移说明（外网 → 内网）

> 面向内网部署执行者（或内网 AI）。这是一份**增量**说明：内网已有 mcp-server 的
> 基础部署（strategyqa 等），本次只需把新增的业务场景补进去。
> 从零部署请看同目录的 `内网部署清单.md`。
>
> **本次已确认的关键前提**：新增场景的表与 `strategyqa`、`mcp_api_keys`、
> `mcp_businesses` **在同一个数据库**。因此：
> - 所有 `*_SCHEMA` 一律**留空**（留空 = 用 `MYSQL_DATABASE`）
> - `.env` 里**只需要配一个库**
> - 内网现有的另外两个数据库配置**本次不需要**

---

## 0. 全局概览

| 项 | 内容 |
|---|---|
| 要拷的代码 | `mcp-server/` **整个目录** |
| 要改的配置 | `.env` 里的 MySQL 连接（**一个库**）+ `MCP_ALLOWED_HOSTS` |
| 要建的表 | `mcp_api_keys`、`mcp_businesses`（mcp-server 启动自愈，或手工建） |
| 要签的 Key | 每个「用户 × 业务」一把 |
| 验证方式 | `scripts/check_tables.py` 核对表 + HTTP 冒烟 |
| 依赖 | 不用装 Python 包以外的任何东西（无 Node、无外部服务） |

## 1. 本次涉及的业务场景与表

**8 个业务包 = 8 个独立 MCP 端点**，每个形如 `http://<地址>:8174/mcp/<业务名>/`，
各自一把 API Key、各自一份表可见性白名单。

| # | 业务名（URL 后缀） | 场景说明 | 表（张数） |
|---|---|---|---|
| — | `strategyqa` | 策略问数（**内网已有**） | `fmut2_strategy_manage`(1) |
| — | `fxbar` | 外汇 K 线（**本次不带**，见 §5.7） | `HSDC_HDS2_BAR_FX`(1) |
| 1 | `idata` | iData 数据分析看板 | `fmqt_bond_exec_part_data`、`fmqt_bond_trade_counterpart_analysis`、`fmqt_bond_lending_analysis`、`fmqt_idata_llm_analysis`(4) |
| 2 | `macro_forecast` | 国内宏观经济指标预测 | `fmqt_forecast_report_meta`、`fmqt_forecast_indicator`、`fmqt_forecast_prediction`、`fmqt_forecast_feature_contribution`、`fmqt_forecast_selected_feature`、`fmqt_forecast_analysis`(6) |
| 3 | `rates_timing` | 10 年期国债趋势判断 | `fmqt_predictions_rates`、`fmqt_prediction_runs_rates`(2) |
| 4 | `weekly_research` | 研报观点矩阵与机构宏观预测 | `weekly_analyzer_data`、`weekly_macro_data`(2) |
| 5 | `gold_analysis` | 黄金价格多因子归因 | `fmqt_gold_analysis_result`(1) |
| 6 | `treasury_1y` | 1 年期国债模型 | `fmqt_treasury_1y_history`(1) |

**去重合计 16 张表**（不含 strategyqa / fxbar 各那 1 张）。

> 📌 **本次通常是"从 1 个业务扩到 8 个"**：内网若只有 `strategyqa`，那本次新增
> 的就是上面 1–6 号共 6 个业务包。

> 📌 **服务名已统一为中文**：各业务包 `server.py` 里 `FastMCP(...)` 的第一个参数
> （即 MCP 握手时返回的 `serverInfo.name`）都是中文：
>
> | 业务 | 服务名 |
> |---|---|
> | `strategyqa` | 策略问数 |
> | `idata` | iData 数据分析看板 |
> | `macro_forecast` | 国内宏观指标预测 |
> | `rates_timing` | 10 年期国债趋势判断 |
> | `weekly_research` | 研报观点矩阵 |
> | `gold_analysis` | 黄金价格驱动因子 |
> | `treasury_1y` | 1 年期国债模型 |
> | `fxbar` | 外汇 K 线 |
>
> 它**只影响握手的展示名，不影响工具名**（工具名由 `@mcp.tool()` 的函数名决定）。
> ⚠️ 若内网之前就地改过这里（比如把 `strategyqa` 改成别的中文名），覆盖后会统一
> 成上表这套 —— 迁移前先 diff 确认一下，避免名字被换掉。
>
> ⚠️ 代码要**整体覆盖** `easy_mcp_server/` 与 `scripts/`，**不要逐个文件挑**——
> `querykit/`、`contract.py`、`registry.py`、`keys.py` 这些共享底座必须与业务包
> 版本配套，混用会出现难查的行为差异（比如模型能看到哪些表变了）。

> ⚠️ **表名易错点**：业务方提供的 SQL 清单里把周报观点表写作 `weekly_data`，
> **实际库中是 `weekly_analyzer_data`**。代码已按实际表名修正，并有测试钉住；
> 若内网核对时发现对不上，以**业务库实际表名**为准。

## 2. 迁移步骤

### 步骤 1：拷贝代码（⚠️ 绝不要动内网已有的 `.env`）

**内网的 `.env` 是你们自己维护的配置**（库地址、密码，以及那另外两个数据库），
本次迁移**必须保留它**。所以打包用**正向指定清单**，而不是 `tar` 整个目录：

```powershell
cd mcp-server

# 1) 代码 + 依赖描述 + 配置模板。注意：整条命令里没有 .env，也没有 .venv
#    fxbar 的表在另一个库（本次不需要），所以连它的包 / 测试 / 脚本一起排除，
#    否则 tests/test_fxbar.py 会让 pytest 收集报错
tar -czf ..\mcp-server-新增场景.tar.gz `
    --exclude=__pycache__ --exclude=.pytest_cache `
    --exclude="easy_mcp_server/businesses/fxbar" `
    --exclude="tests/test_fxbar.py" `
    --exclude="scripts/seed_fxbar_demo.py" --exclude="scripts/smoke_fxbar.py" `
    easy_mcp_server scripts tests pyproject.toml uv.lock .env.example
```

**2) 文档单独拷**（Windows 自带 `tar` 打中文文件名解压后可能乱码，单独拷也便于你挑着给）：

```
README.md
内网迁移说明_新增场景.md
内网部署清单.md
iData-MCP工具设计.md    iData数据分析看板.md
1年期国债模型_SQL清单_MCP信息.md
```

**内网落盘方式**（覆盖到现有 `mcp-server/`，**保留 `.env`**）：

```bash
cd <内网 mcp-server 的上级目录>

cp -a mcp-server mcp-server.bak.$(date +%Y%m%d)   # ★ 先备份，方便回滚
tar -xzf mcp-server-新增场景.tar.gz               # 覆盖 easy_mcp_server/ scripts/ tests/ 等
# 文档手工放进 mcp-server/
```

解压后**确认这两件事**：

```bash
ls -la mcp-server/.env          # ← 必须还是你们原来那份（三个库配置都在）
cd mcp-server
uv run python -m scripts.check_tables --quiet     # ← 用现有 .env 就能核对表
```

> **为什么不用"整个目录 + 排除"**：即使加了 `--exclude=.env` 也不会覆盖 `.env`，
> 但整目录打包容易顺带带上 `logs/`、`workspace/`、`*.tar.gz` 等运行时产物；
> 更麻烦的是，内网若在 `mcp-server/` 下放过自定义文件，覆盖式解压会**悄悄替换**它们。
> 正向指定清单最可控。

**要带 / 不要带**：

| 带上 | 不要带 |
|---|---|
| `easy_mcp_server/`（全部业务包 + `querykit/` + `contract.py` / `registry.py` / `keys.py`…） | **`.env`** ⚠️ 内网自己的配置，绝对不要覆盖 |
| `scripts/`（`init_keys.py`、`check_tables.py`、`retire_business.py`…） | `.venv/` ⚠️ 写死了外网 Python 绝对路径 |
| `tests/`（想在内网跑测试就带） | `__pycache__/`、`.pytest_cache/` |
| `pyproject.toml`、`uv.lock` | `logs/`、`workspace/`（运行时产物） |
| `.env.example`（模板，仅作填写参考） | `*.tar.gz`（打包产物本身） |
| `*.md` 文档 | `scripts/seed_*_demo.py`、`scripts/smoke_*`（演示数据脚本，可选） |

> ⚠️ 覆盖之前那句 `cp -a` 备份不能省：内网若曾就地改过 `easy_mcp_server/` 里的东西
> （适配内网的库名、表名等），覆盖后就找不回来了。

#### 能不能"只动业务包"（只带 `businesses/`）？❌ 不行

业务清单是**目录扫描**出来的，这一点很好：`contract.business_names()` 只
`pkgutil.iter_modules` 扫 `businesses/` 下的包名（刻意不 import），`app.py`
再动态 `import_module` 并自动 mount 到 `/mcp/<包名>/`。**所以新增业务包本身
不需要改任何共享代码**。

**但只带 `businesses/` 会在启动时直接报错**：

```python
# 每个新增业务包的 server.py 都有这一行
return policy_from_env("IDATA_", default_allowed=idata.default_allowed_tables())
                                              ↑ querykit/explore.py 里后加的参数
```

`default_allowed` 是 `querykit/explore.py` 新增的参数。内网的 `querykit/` 是为
strategyqa 部署的，**很可能没有它** → 6 个新增业务在 import 阶段就会抛：

```
TypeError: policy_from_env() got an unexpected keyword argument 'default_allowed'
```

业务包对共享底座的依赖（`from ...xxx import`）：

| 依赖 | 说明 |
|---|---|
| **`querykit/`** | 用得最多：`policy_from_env`（就是上面那个）、`readonly_query`、`assert_identifier`、`list_tables`、`describe_table`… |
| `context.py`、`env.py` | 取当前用户名、读环境变量 |

**所以两个选择**：

| 方案 | 带什么 | 说明 |
|---|---|---|
| **推荐：整体覆盖** | `easy_mcp_server/` + `scripts/` | 差异只有几十 KB，能保证 `querykit`/`contract`/`app`/`registry` 全部配套 |
| **最小集** | `businesses/` + **`querykit/`** | `querykit/` 必须带上，否则必炸；其余顶层文件仍建议先 diff 再决定 |

**更稳的做法：先 diff 再精确覆盖**（完全不会碰到内网的自定义改动）：

```bash
# 新代码解到临时目录，逐目录比对
mkdir -p /tmp/mcp-new && tar -xzf mcp-server-新增场景.tar.gz -C /tmp/mcp-new
diff -rq /tmp/mcp-new/easy_mcp_server mcp-server/easy_mcp_server
```

- 输出 `Only in mcp-server/...` → **内网独有**（可能是你们的改动，**别覆盖**）
- 输出 `differ` → 双方都有但内容不同，**逐个确认后再拷**
- 输出 `Only in /tmp/mcp-new/...` → 本次新增，直接补进去

#### ✅ 最小可行集（只同步"业务相关"代码，配置完全不动）

如果内网已有可用的 mcp-server（业务注册表那版），**只需要下面这些**：

```powershell
cd mcp-server

tar -czf ..\mcp-server-新增场景.tar.gz `
    --exclude=__pycache__ `
    --exclude="easy_mcp_server/businesses/fxbar" `
    easy_mcp_server/businesses `
    easy_mcp_server/querykit/explore.py `
    scripts/check_tables.py scripts/init_keys.py
```

| 路径 | 为什么 |
|---|---|
| `easy_mcp_server/businesses/` | 6 个新增业务包；同时带上原有包的改动（服务名改中文、白名单汇总） |
| **`easy_mcp_server/querykit/explore.py`** | ⚠️ **必带** —— `policy_from_env` 新增的 `default_allowed` 参数，6 个业务包全在用；内网那份没有它会在 import 阶段 `TypeError` |
| `scripts/check_tables.py` | 表核对工具（已纳入 6 个新场景）；不带也能跑，只是核对不方便 |
| `scripts/init_keys.py` | 新增 `--revoke` / `--list`；不带不影响服务运行 |

**其余共享文件都不用动**。我核对过外网相对内网基线（引入业务注册表的那次重构）的差异：

| 文件 | 差异 |
|---|---|
| `contract.py`、`registry.py`、`app.py`、`db.py`、`env.py`、`context.py`、`auth.py`、`main.py` | **零改动** ✅ |
| `keys.py` | 仅 2 行 docstring |

原因是端点挂载走 `contract.business_names()` —— 它**扫描 `businesses/` 目录**得到清单，`app.py` 再动态 import 并挂到 `/mcp/<包名>/`。所以**新增包放进去就自动生效，不需要改任何顶层文件**。

#### 配置：一个字都不用改 ✅

| 配置项 | 动不动 | 说明 |
|---|---|---|
| `MYSQL_HOST` / `PORT` / `USER` / `PASSWORD` / `DATABASE` / `CHARSET` | **不动** | 新增 6 个场景与策略问数**同库** |
| `IDATA_SCHEMA` / `FORECAST_SCHEMA` / `RATES_SCHEMA` / `WEEKLY_RESEARCH_SCHEMA` / `GOLD_SCHEMA` / `TREASURY_1Y_SCHEMA` | **不用写** | 留空 = 用 `MYSQL_DATABASE`；只有表在别的库才需要填 |
| 各 `*_ALLOWED_TABLES` | **不用写** | 代码缺省已把白名单收敛到各业务自己的表 |
| `MCP_ALLOWED_HOSTS` / `MCP_ALLOWED_ORIGINS` | **不动** | 之前能正常访问就继续能用 |
| `STRATEGY_TABLE` | **不动** | |
| `QUERYKIT_MAX_ROWS` / `QUERYKIT_TIMEOUT_MS` / `QUERYKIT_POOL_SIZE` | **不动** | |
| `MCP_KEY_CACHE_TTL` | **不动** | 吊销后最多这么久失效 |

> 也就是说：**拷贝完代码直接启动即可**，`.env` 保持原样。

### 步骤 2：安装依赖

```bash
cd mcp-server
uv sync                 # 内网要配好 uv 的镜像源
# 或者已经装过一次，只需
uv sync --frozen
```

> ⚠️ **若内网已有自己的 `uv.lock` 且能跑通，不要用外网这份覆盖**——两份混用会撞出
> 版本冲突（典型症状：`uvicorn<0.30.0` 与 `mcp>=1.27.0` 互斥）。

### 步骤 3：配置 `.env`

```bash
cp .env.example .env
```

**只需改这几项**（因为新增场景与 strategyqa 同库）：

```bash
MYSQL_HOST=<内网库地址>
MYSQL_PORT=3306
MYSQL_USER=<账号>
MYSQL_PASSWORD=<密码>
MYSQL_DATABASE=<与 strategyqa/mcp_api_keys/mcp_businesses 同一个库名>   # ★ 关键
```

**如果通过域名或反向代理访问**，还必须配（否则所有请求返回 421，且报错不提配置）：

```bash
MCP_ALLOWED_HOSTS=mcp.internal,mcp.internal:8174
MCP_ALLOWED_ORIGINS=http://mcp.internal:8174
```

> `host:*` 只匹配**带端口**的 Host；http/https 默认端口的 Host 不带端口，
> 所以两种写法都要列。走 `127.0.0.1` 访问则不需要配。

**各场景的 `*_SCHEMA` 全部保持注释状态（留空）** —— 因为表都在 `MYSQL_DATABASE` 里：

```bash
# IDATA_SCHEMA=
# FORECAST_SCHEMA=
# RATES_SCHEMA=
# WEEKLY_RESEARCH_SCHEMA=
# GOLD_SCHEMA=
# TREASURY_1Y_SCHEMA=
```

`*_ALLOWED_TABLES` 也不用配——代码里缺省已把白名单收敛到各业务自己的表，
模型做结构探索时只能看到自己那几张表。

### 步骤 4：建表

需要两张表。**mcp-server 启动时会自愈建 `mcp_businesses`**，`mcp_api_keys` 由
`init_keys.py` 建。一次搞定：

```bash
uv run python -m scripts.init_keys --only-create-table
```

输出 `表 mcp_api_keys 已就绪` 即成功。

> ⚠️ **如果 mcp-server 用的是只读账号**，自愈建表会失败。而 `publish()` 只告警不阻断
> ——服务照常启动，但业务注册表为空，主应用会回退内置清单、看不到新业务。
> 三种处理方式任选：
> 1. 先跑一次 `init_keys.py --only-create-table`（用有建表权限的账号）
> 2. 临时 `GRANT CREATE ON <库>.*`，建完收回
> 3. 手工执行建表 SQL（见 `内网部署清单.md` §4.2）

### 步骤 5：签发 API Key

**每个用户 × 每个业务一把**。可以给某个用户一次签发全部业务：

```bash
# 查看当前有哪些 Key（不会显示明文，只有状态）
uv run python -m scripts.init_keys --list

# 给指定用户签发指定业务（明文只显示一次，务必当场记录）
uv run python -m scripts.init_keys -u <用户名> -b idata
uv run python -m scripts.init_keys -u <用户名> -b macro_forecast
uv run python -m scripts.init_keys -u <用户名> -b rates_timing
uv run python -m scripts.init_keys -u <用户名> -b weekly_research
uv run python -m scripts.init_keys -u <用户名> -b gold_analysis
uv run python -m scripts.init_keys -u <用户名> -b treasury_1y

# 吊销（旧 Key 立即失效，注意校验侧有 60s 缓存）
uv run python -m scripts.init_keys -u <用户名> -b idata --revoke
```

> 用户名**必须与主应用的登录账号一致**（`strategyqa` 还有行级隔离：
> 只返回 `AUTHOR = 当前账号` 的策略，不一致会永远查不到数据）。

拿到明文后，写进用户的 MCP 配置（`workspace/{用户名}/mcp.json`）：

```json
{
  "servers": {
    "idata": {
      "transport": "streamable_http",
      "url": "http://<mcp 地址>:8174/mcp/idata/",
      "headers": { "Authorization": "Bearer <上面签发的明文>" }
    }
  }
}
```

> 主应用侧若仍保留设置页/连接器页，也可以从界面添加——自家业务会自动注入 Key，
> 无需手工粘贴（见 `内网部署清单.md` §6.2）。

### 步骤 6：启动

```bash
uv run uvicorn easy_mcp_server.main:app --host 0.0.0.0 --port 8174 \
    --timeout-graceful-shutdown 5
```

**启动日志要看到三个检查点**：

1. `[mcp-server] MySQL 目标: <host>:<port>/<database>` —— **核对库名对不对**
2. 各业务注册成功、没有 `publish` 告警
3. 监听端口就绪

### 步骤 7：验证

**7.1 核对表（最关键的一步）**

```bash
uv run python -m scripts.check_tables        # 逐表输出 OK / MISS
uv run python -m scripts.check_tables --quiet  # 只输出缺失项与小结
```

- 退出码 **0** = 全部存在 ✅
- 退出码 **1** = 有缺失，脚本会打印缺失清单和排查方向

**期望结果**：

| 情况 | 输出 | 退出码 |
|---|---|---|
| **不带 fxbar**（本次推荐） | `小结: 17/17 张表存在` | 0 |
| 带了 `businesses/fxbar/` | `小结: 18/18 张表存在` | 0 |

即 16 张新增 + strategyqa 1 张 = 17。fxbar 的表在**另一个库**（本次不需要），
所以建议不拷 `businesses/fxbar/` —— 那时脚本也不会把它计入总数。

**7.2 HTTP 冒烟**

```bash
# 免鉴权健康检查
curl http://127.0.0.1:8174/health

# 带 Key 调一个业务端点（未带 Key 应返回 401）
curl -H "Authorization: Bearer <明文>" http://127.0.0.1:8174/mcp/idata/
```

**7.3 端到端**

在主应用里对该业务提一个自然语言问题，确认 MCP 工具被调用、返回真实数据。

- [ ] `check_tables.py` 退出码为 0（表全在）
- [ ] `mcp_api_keys`、`mcp_businesses` 两张表存在
- [ ] 每个需要访问的用户 × 每个业务都签发了 Key
- [ ] 用户配置里 `Authorization: Bearer <明文>` 正确、URL 后缀与业务名一致
- [ ] 未带 Key 的请求返回 **401**（不是 200、也不是 421）
- [ ] 各业务提一个真实问题，能返回数据

## 4. 注意事项 / 常见坑

| # | 坑 | 症状与处理 |
|---|---|---|
| 0 | **覆盖了内网的 `.env`** ⚠️ | 库地址/密码被换掉，服务连不上库。**打包时不要带 `.env`**（见 §步骤 1）；升级前先 `cp -a` 备份整个目录 |
| 1 | **库不一致** | 主应用签发了 Key，MCP 一律 **401**，且没有任何报错指向配置。核对启动日志的 `MySQL 目标` 那行 |
| 2 | **只读账号导致建表失败** | 服务能起，但主应用看不到新业务。看日志里 `publish`/建表告警，按 §步骤 4 处理 |
| 3 | **`MCP_ALLOWED_HOSTS` 没配** | 通过域名访问全部 **421**，报错完全不提这个配置。见 §步骤 3 |
| 4 | **事务隔离** | `check_tables.py` 查的是 `information_schema`，如果只读账号没这个库的可见权限会误报 MISS |
| 5 | **表名对不上** | 优先确认业务库实际表名（如 `weekly_analyzer_data` 不是 `weekly_data`）。改动集中在各场景模块顶部的 `TABLES` 常量区，改完 `uv run pytest tests/ -q` 验证，不用连库 |
| 6 | **Key 明文只有一次** | 库里只存 sha256，丢了只能重签（旧 Key 立即作废） |
| 7 | **fxbar 本次不带** | 若无外汇 K 线需求，不要拷 `businesses/fxbar/`、`tests/test_fxbar.py`、`scripts/*fxbar*`（否则 pytest 收集报错）。表 `HSDC_HDS2_BAR_FX` 也无需核对 |
| 8 | **连接池与 MySQL 上限** | `QUERYKIT_POOL_SIZE` 缺省 5，**多进程部署时实际连接数 = 进程数 × 该值**，要小于 MySQL `max_connections` |
| 9 | **吊销有缓存** | `MCP_KEY_CACHE_TTL` 缺省 60s，吊销后最多 1 分钟内旧 Key 仍可能通过 |

---

## 5. 回滚

新增业务是**纯追加**的，回滚只需：

1. 停掉 mcp-server
2. 从主应用的用户配置里删掉对应 `servers` 条目
3. 清理共享库里的残留（业务注册 + Key）：

```bash
uv run python -m scripts.retire_business <业务名>          # 先预览
uv run python -m scripts.retire_business <业务名> --apply   # 实际执行
```

> `retire_business` 会要求该业务包**已不在** `businesses/` 下才放行——回滚时先把
> 对应目录移走。

数据库表（`fmqt_*` 等）**不要删**，它们是业务方自己写入的结果表，与 MCP 服务无关。
